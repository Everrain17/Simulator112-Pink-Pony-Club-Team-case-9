# System112 — техническая документация

## 1. Назначение проекта

**System112** — учебно-симуляционная система для подготовки и оценки операторов системы экстренного вызова **112**.

Основная задача системы — создать контролируемую виртуальную рабочую среду, в которой обучаемый взаимодействует с входящими вызовами, ведёт диалог с виртуальным заявителем, получает информацию о происшествии, заполняет карточку оператора и выбирает необходимые службы.

Система фиксирует ход работы обучаемого и позволяет преподавателю анализировать результат выполнения задания.

В отличие от простого интерфейсного тренажёра System112 включает:

* симуляционное ядро;
* серверное взаимодействие;
* виртуального заявителя;
* голосовой ввод и вывод;
* классификацию происшествий;
* контроль действий оператора;
* сохранение результатов;
* автоматический анализ и оценку;
* интерфейс обучаемого;
* интерфейс преподавателя;
* административный инструмент.

# 3. Состав системы

## 3.1. Python Backend

Расположен в:

```text
serv-112/backend/
```

Основные функции:

* работа с пользователями;
* работа со сценариями;
* хранение реплик сценариев;
* работа с классификаторами;

* резервное копирование;
* взаимодействие с runtime и C#-компонентами;

Python Backend является центральной серверной точкой доступа для административного инструмента и клиентских интерфейсов.

# 4. Admin Tool

Расположен в:

```text
serv-112/admin_tool/
```

Admin Tool представляет собой desktop-приложение на **PySide6**.

Он используется администратором и преподавателем для управления серверной частью системы.

Основные функции:

* вход в систему;
* управление пользователями;
* управление сценариями;
* редактирование реплик сценариев;
* работа с классификаторами;
* просмотр вызовов;
* просмотр трасс;
* просмотр журнала аудита;
* изменение системных настроек;
* управление резервными копиями;
* мониторинг состояния backend;
* запуск и остановка серверной части.

Admin Tool взаимодействует с Python Backend через HTTP(S) и использует Bearer-токены для авторизации.

API-клиент реализован отдельным классом `ApiClient`, который также отвечает за автоматическое обновление access token.

# 5. C# Backend

Исходный код C# серверной части расположен в:

```text
SimCore/
```

C#-контур отвечает за симуляционную логику.

Ключевая часть системы — симуляционное ядро `SimCore.Engine`.

Ядро формирует и поддерживает состояние виртуального мира, включая:

* активные вызовы;
* происшествия;
* журнал действий оператора;
* системный журнал событий;
* активные сессии;
* состояние заявителя;
* состояние карточки;
* временные параметры сценария.

В состоянии движка используются сущности:

```text
WorldState
ActiveCall
Incident
CallerState
```

и связанные перечисления и структуры.

# 6. Симуляционное ядро

Основная задача C# ядра — моделировать поведение виртуального вызова.

При создании вызова формируются:

* уникальный `CallId`;
* идентификатор происшествия;
* виртуальный заявитель;
* уровень паники;
* эмоциональное состояние;
* степень сотрудничества;
* первоначальная реплика;
* состояние карточки;
* временные ограничения.

Пример жизненного цикла:

```text
Создание сценарного вызова
          ↓
Создание Incident
          ↓

          ↓

          ↓

          ↓

          ↓

          ↓

          ↓
Завершение
          ↓

          ↓

```

# 7. Виртуальный заявитель

Заявитель является частью состояния `ActiveCall`.

Для него отслеживаются, в частности:

* идентификатор;
* эмоциональное состояние;
* уровень паники;
* готовность сотрудничать;
* последняя реплика;
* наличие предоставленного адреса;
* наличие информации о пострадавших;
* состояние завершения звонка;
* скорость речи.

Уровень паники влияет на поведение заявителя и используется системой анализа.

В WebSocket-телеметрии C# backend передаёт клиенту:

```text
panicLevel
silenceDurationSeconds
hasGivenAddress
hasGivenVictimsInfo
accumulatedWordsCount
```

Таким образом система может отслеживать не только факт разговора, но и динамику его прохождения.

# 9. Классификация происшествий

В системе используется классификатор происшествий.

Он используется для определения типа события и связанных с ним признаков.

Система работает с такими логическими категориями, как:

```text
IncidentType
ServiceType
ClassifierTag
```

В классификаторе учитываются:

* тип происшествия;
* необходимые службы;
* дополнительные признаки;
* классификационные теги.

C#-часть умеет загружать классификатор из:

```text
incident-classifier.json
```

Если значение невозможно определить, используются предусмотренные значения по умолчанию.

# 10. Вызов и его идентификация

Каждый вызов имеет собственный идентификатор:

```text
CallId
```

Идентификатор используется для связывания:

* звонка;
* карточки оператора;
* событий;
* анализа;
* WebSocket-сеанса;
* сохранённых данных;
* оценки.

На клиентской стороне дополнительно формируется номер происшествия, например:

```text
12345678-0001
```

При открытии карточки `CallId` передаётся напрямую в URL карточки.

Это позволяет гарантировать, что карточка относится именно к текущему вызову, а не к случайному локальному идентификатору.

# 11. Приём входящего вызова

Рабочий сценарий обучаемого начинается с появления входящего вызова.

Клиент регулярно получает текущее состояние runtime.

Если обнаруживается вызов, находящийся в состоянии:

```text
Свободен
```

обучаемому показывается окно входящего вызова.

В интерфейсе отображается номер заявителя.

После нажатия кнопки принятия выполняется запрос к runtime.

Передаются:

```text
callId
studentId
sessionId
phoneNumber
```

После успешного принятия:

* вызов закрепляется за обучаемым;
* обновляются данные пользователя;
* запускается таймер разговора;
* разрешается открытие карточки;
* запускается голосовой контур.

# 12. Голосовой контур

Голосовой контур системы состоит из двух основных частей:

```text
STT
TTS
```

## STT

Для распознавания речи используется **Vosk**.

Используется русская модель:

```text
vosk-model-small-ru-0.22
```

Микрофон обучаемого подключается через браузерный API:

```text
navigator.mediaDevices.getUserMedia()
```

Полученные аудиоданные преобразуются в PCM и передаются в WebSocket.

---

# 13. TTS

Для синтеза речи используется **Silero v5**.

TTS-сервер расположен в:

```text
tts-server/
```

Основная модель:

```text
v5_ru.pt
```

Сервер написан на Python и использует:

```text
FastAPI
PyTorch
SciPy
Vosk
num2words
```

Синтез может использовать CPU либо CUDA в зависимости от доступности GPU.

HTTP endpoint:

```text
POST /v1/audio/speech
```

Для запроса передаётся текст и дополнительные параметры, в том числе:

```text
input
gender
panic_level
```

Аудио возвращается как WAV-поток.

# 14. WebSocket голосового диалога

Для непосредственного ведения диалога используется WebSocket C# backend:

```text
/api/stream-call
```

В URL передаётся:

```text
callId
```

WebSocket используется для двух направлений.

## От обучаемого к серверу

STT распознаёт речь и передаёт текст:

```json
{
    "type": "interim",
    "text": "..."
}
```

или:

```json
{
    "type": "final",
    "text": "..."
}
```

C# backend получает этот текст и передаёт его в симуляционную логику.

## От сервера к обучаемому

Сервер может отправлять:

* текстовые сообщения;
* аудиоданные;
* команды управления воспроизведением;
* телеметрию.

В частности, применяется команда:

```text
stop_audio
```

для прекращения текущего воспроизведения, если заявитель должен быть перебит оператором.

# 16. Карточка оператора

В интерфейсе предусмотрены поля:

* тип происшествия;
* оператор;
* телефон;
* заявитель;
* адрес;
* описание.

Также карточка содержит структурированные данные:

* классификатор;
* службы;
* флаги;
* checklist;
* данные заявителя;
* телефон;
* дополнительные параметры оценки.

# 17. Сохранение карточки

Сохранение карточки проходит через два основных этапа.

Сначала карточка отправляется серверу:

```text
POST /runtime/calls/{callId}/card
```

После этого вызывается завершение:

```text
POST /runtime/calls/{callId}/complete
```

После успешного завершения клиент получает результат, содержащий, помимо прочего:

```text
evaluation
```

Информация об успешном сохранении также передаётся обратно в окно журнала через:

```text
window.postMessage()
```

с событием:

```text
CARD_SAVED
```

После получения этого события кнопка повторного создания карточки блокируется.

# 18. Завершение звонка

Вызов может завершаться из интерфейса текущего разговора.

Используется endpoint:

```text
POST /runtime/calls/{callId}/finish
```

После успешного завершения:

* закрывается карточка;
* останавливается голосовой поток;
* освобождается микрофон;
* закрываются WebSocket;
* сбрасывается таймер;
* скрывается виджет текущего звонка;
* обновляется состояние системы.

При сохранении карточки дополнительно используется операция `complete`, которая фиксирует результат обработки вызова.

# 21. Хранение результатов

Результаты учебной работы не должны зависеть от того, запущен ли в данный момент текущий звонок.

Для этого сервер хранит завершённые данные отдельно.

Для карточек используются JSON-файлы в C#-части:

```text
wwwroot/sessions/
```

Имя файла строится на основе `CallId`:

```text
wwwroot/sessions/{CallId}.json
```

C# backend также имеет endpoint загрузки ранее сохранённых карточек.

Таким образом завершённый вызов может быть восстановлен после завершения текущей сессии симуляции.

# 25. Qwen

Для генерации текста виртуального заявителя используется локальный сервер LLM.

Используется:

```text
llama-server.exe
```

Модель:

```text
qwen2.5-14b-instruct-q4_k_m.gguf
```

Типовая конфигурация:

```text
Host: 0.0.0.0
Port: 8080
```

Qwen работает локально и не требует внешнего API во время стандартной работы системы.

В текущей конфигурации используется готовая базовая модель Qwen 2.5 14B Instruct. Специализированного fine-tuning именно под System112 в текущем проекте нет.

```text
Alembic
```

# 28. Redis

# 29. Docker


Затем система ожидает готовности PostgreSQL и запускает миграции Alembic.

# 31. Адрес серверного компьютера

Система использует IP-адрес серверного компьютера для подключения клиентских компонентов.

Конфигурация Python Backend содержит:

```python
SERVER_HOST
SERVER_PORT
```

При переносе серверной части на другой компьютер старый IP может измениться.

Для автоматического обновления IP используется:

```text
ip_set.bat
```

Скрипт получает текущий IPv4 серверного компьютера и обновляет значение `SERVER_HOST` в:

```text
serv-112/admin_tool/config.py
```

Благодаря этому перенос серверной части на новый компьютер не требует ручного поиска и замены старого IP.

# 32. TLS

Python Backend поддерживает работу через HTTPS.

Основные настройки:

```text
SSL_ENABLED
SSL_CERT_FILE
SSL_KEY_FILE
SSL_CA_FILE
SSL_VERIFY_CLIENT
```

По умолчанию серверный сертификат используется для HTTPS.

Поддерживается режим взаимной TLS-аутентификации, однако в текущей конфигурации:

```text
SSL_VERIFY_CLIENT=false
```

то есть проверяется сертификат сервера без обязательной проверки клиентского сертификата.

# 35. Сессии

Сессия связывает учебный запуск с действиями участников.

В клиентской части используется:

```text
sessionId
```

Он может передаваться в URL и храниться локально.

При принятии вызова `sessionId` передаётся в runtime.

Это позволяет связывать отдельные вызовы с конкретным запуском симуляции.

---

# 36. Мониторинг

Admin Tool содержит отдельный `Monitor`.

Монитор отслеживает состояние backend и позволяет отображать:

```text
stopped
starting
running
stopping
failed
```

ServerManager также следит за процессом backend через watchdog.

При завершении процесса состояние переводится в:

```text
failed
```

---

# 37. Управление процессами

`ServerManager` отвечает за запуск Python Backend.

Он:

* проверяет занятость порта;
* ищет владельца порта;
* определяет ранее запущенный backend;
* записывает PID;
* запускает `uvicorn`;
* отслеживает процесс;
* ведёт лог;
* поддерживает остановку;
* поддерживает перезапуск;
* умеет освобождать порт от осиротевшего Python/Uvicorn-процесса.

PID backend хранится в:

```text
logs/backend.pid
```

# 52. Жизненный цикл учебной сессии

Типовой учебный процесс:

```text
1. Преподаватель запускает систему
        ↓
2. Сервер поднимает необходимые компоненты
        ↓
3. Запускается симуляционное ядро
        ↓
4. Система создаёт или активирует сценарий
        ↓
5. Формируется входящий вызов
        ↓
6. Обучаемый принимает вызов
        ↓
7. Запускается речевой контур
        ↓
8. Выполняется диалог
        ↓
9. Система контролирует действия оператора
        ↓
10. Обучаемый заполняет карточку
        ↓
11. Карточка отправляется серверу
        ↓
12. Вызов завершается
        ↓
13. Формируется результат оценки
        ↓
14. Данные сохраняются
        ↓
15. Преподаватель анализирует результат
```

# 55. Текущие ограничения

На текущем этапе существуют ограничения, связанные прежде всего с внешними зависимостями среды:

* для серверного компьютера необходим Docker Desktop;
* для C# Backend необходим установленный .NET SDK;
* для TTS необходимо окружение Python с PyTorch и остальными зависимостями;
* для Qwen требуется файл GGUF-модели;
* AI-контур использует готовую базовую Qwen-модель без специализированного обучения под System112;
* серверный компьютер должен иметь доступ к нужным сетевым интерфейсам;
* клиентские компьютеры должны иметь сетевой доступ к серверу.
